# fielddb

A header-only C++23 storage engine that logs **per field instead of per record**, a single-header
distribution of it, and **fielddb**, a database layer on top (MVCC, ten secondary indexes, triggers,
asynchronous commit) that is benchmarked against PostgreSQL.

> **Status and honesty note.** The engine is the product of this repository's history. The `fielddb/`
> layer and every benchmark number about it come from a **quickly assembled test build**: a
> production-style database layer, **not a production-hardened release**. Figures are indicative.
> Details: [`fielddb/README.md`](fielddb/README.md), [`fielddb/docs/BENCHMARKS.md`](fielddb/docs/BENCHMARKS.md),
> [`fielddb/docs/REVIEW.md`](fielddb/docs/REVIEW.md).

## The engine in one paragraph

One append-only log over `mmap`, indexed per **field** rather than per record. Nothing is patched in place,
so changing eight bytes of a kilobyte record writes eight bytes, where a B+tree or a heap table rewrites the
row. Reads are a gather over the record's base plus its overrides, so reads are the cost, and that cost shows
only while the data fits in RAM. One writer per instance is the unit of scale; independent instances scale
across cores.

Measured by the upstream benchmarks (1 KB records, 1-core 960 MB VPS, page cache dropped between cells):

| | Field | LMDB | ObjectBox |
|---|---|---|---|
| random update (1 GB on 960 MB RAM, 10,000-record crash window) | **543,070 ops/s** | 2,308 | 1,758 |
| major page faults over 300,000 updates | **164** | 180,305 | 229,770 |
| iowait during the update phase | **0.01 s** | 90.74 s | 116.59 s |
| on disk per 1 GB of data | **1.05 GB** | 1.34 GB | 2.11 GB |

The update column is the design: an append touches no page of the record, so there is nothing to fault on
and nothing to wait for. Both in-place designs stall on the device. See
[`storage/FIELD_STORAGE.md`](storage/FIELD_STORAGE.md) for the full specification and
[`fielddb/docs/BENCHMARKS.md`](fielddb/docs/BENCHMARKS.md) for the complete tables and what each benchmark program answers.

## Using it

The engine needs only the standard library and POSIX. Take one file:

```cpp
#include "field_storage.hpp"      // dist/field_storage.hpp: copy it and go
```

or three, keeping their relative layout: `storage/storage.hpp`, `storage/field_storage.hpp`, `embedded/platform.hpp`.
`dist/field_storage.hpp` is generated by `tools/amalgamate.py`; `ctest` regenerates and diffs it, and a
separate case compiles a translation unit that includes it and nothing else.

```cpp
struct account {
    static constexpr storage::tag_t tag = 1;
    uint64_t balance, opened_ms;
    char     name[64];
};

using spec = storage::field_spec<
    "data.log", 8ull << 30,      // the log
    "data.idx", 1'000'000,       // one 16-byte slot per id ever issued
    200'000,                     // override nodes
    8, sizeof(account),          // max chain depth, widest record
    "data.ckp">;                 // enables restart()

storage::field_storage<spec> table;
if (!table.ok()) return 1;
table.restart(8ull << 30);       // falls back to a full replay by itself

const auto id = table.create(account{ 500, now_ms(), "ada" });
table.update<&account::balance>(id, 450);      // writes 8 bytes, not 88
if (auto a = table.get<account>(id)) use(a->balance);

table.sync();                    // durability barrier: see section 8 of the spec before choosing when
```

Two things to know before building on it (both expanded in the spec):

- **`get<T>()` returns a copy, not a pointer.** The current record exists at no single address: the base is
  where it was created and each override is wherever the log happened to be.
- **The barrier must be spaced by more than it costs.** A `sync()` placed at the device's own single-page
  latency spends all its time being the previous one.

## Repository layout

| path | what |
|---|---|
| `storage/` | the modular engine: `field_storage.hpp`, `indexes.hpp`, `blob.hpp`, the heap engine `storage.hpp`, gather helpers, and the specification `FIELD_STORAGE.md` |
| `dist/` | the generated single-header distribution |
| `embedded/`, `runtime/`, `net/uring_ring.hpp` | the small dependencies the engine and its benchmarks use |
| `tests/` | engine tests (doctest) and two fuzzers (`fuzz_storage_recover`, `fuzz_wal_apply_range`) |
| `bench/` | upstream engine benchmarks and probes (LMDB/ObjectBox comparisons, durability-barrier probes, sharding) |
| `tools/` | amalgamation script and smoke tests |
| `examples/expo-android/` | an Expo/Android module built on the engine |
| `fielddb/` | the fixed single-header release, the MVCC database layer, the Postgres comparison harness, results and docs |

## Build and test

```
cmake -S . -B build -G Ninja && cmake --build build && ctest --test-dir build --output-on-failure
```

Needs CMake 3.20+, a C++23 compiler (clang 20 and g++ 14 were used) and doctest. The Postgres comparison
has its own requirements, listed in [`fielddb/README.md`](fielddb/README.md#reproduce).

## The fielddb layer in short

`fielddb/include/field_storage.hpp` is `dist/field_storage.hpp` plus two downstream patches and **five engine
fixes** found by the benchmark (a hash-map erase that loses index rows, an UPDATE silently dropped when the
override arena runs out, two log-corruption bugs in replay and WAL application, and an index that was held
twice in memory). Each fix has a regression test that fails on the original engine
(`fielddb/tests/regress.cpp`). Those bugs still exist in the modular sources under `storage/`, which are kept
as developed.

## History

The history of `storage/`, `dist/`, the tests, the benchmarks and the tools is preserved from the project
this engine was developed in: 71 commits with their original dates, reduced to the paths of this repository.
Commit trailers were removed and every commit is attributed to a single public identity. The `fielddb/`
layer is added on top of that history.
